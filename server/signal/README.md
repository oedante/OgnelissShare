# Служба связи Ogneliss Share (`ogneliss-signal`)

Маленькая служба на Rust для функции «Отдать файлы» без приложения у получателя
(этап 2, `docs/WEB_P2P.md`). Она работает как почтовый ящик: приложение открывает
«комнату», браузер получателя кладёт в неё зашифрованное предложение WebRTC (SDP),
приложение забирает его и кладёт ответ, после чего устройства соединяются напрямую
и файлы идут уже мимо сервера. Служба **ничего не хранит на диске** и **никогда не
видит ни содержимого файлов, ни ключей**: ключ шифрования стоит в ссылке после `#`
и на сервер не отправляется, а `msg` для службы — непрозрачная строка, которую она
не расшифровывает. Состояние живёт только в памяти; перезапуск службы закрывает все
комнаты. Протокол и коды ответов — `docs/WEB_P2P.md`, раздел 2.

Запросы идут на `https://ogneliss.ru/share/api/v1/…`; Nginx Proxy Manager (NPM)
передаёт их в контейнер службы по сети Docker.

## Развёртывание

Нужен сервер с Docker (с плагином Compose) и уже работающим Nginx Proxy Manager,
у которого есть хост `ogneliss.ru`.

1. **Получить файлы.** Каталог `server/signal/` положить на сервер: клонировать
   репозиторий или скопировать каталог целиком (`scp -r server/signal user@сервер:~/ogneliss-signal`).
   Дальше все команды выполняются из этого каталога.

2. **Узнать сеть NPM.** Служба должна быть в той же сети Docker, что и контейнер NPM:

   ```sh
   docker network ls
   ```

   Обычно сеть называется `<каталог NPM>_default`. Если сомневаетесь, посмотрите, в каких
   сетях стоит сам NPM: `docker inspect -f '{{json .NetworkSettings.Networks}}' <контейнер NPM>`.

3. **Настроить Compose.**

   ```sh
   cp docker-compose.example.yml docker-compose.yml
   ```

   В конце файла заменить `npm_default` на настоящее имя сети.

4. **Собрать и запустить** (образ собирается прямо на сервере, реестр не нужен):

   ```sh
   docker compose up -d --build
   ```

   Без Compose то же самое руками:

   ```sh
   docker build -t ogneliss-signal .
   docker run -d --name ogneliss-signal --restart unless-stopped \
     --network npm_default --read-only --cap-drop ALL \
     --security-opt no-new-privileges:true --memory 64m ogneliss-signal
   ```

   Порт наружу публиковать не нужно: NPM обращается к службе по имени
   контейнера `ogneliss-signal` и порту `8080`.

5. **Подключить к NPM.** Nginx Proxy Manager → Hosts → Proxy Hosts → `ogneliss.ru` →
   Edit → вкладка Advanced → в поле Custom Nginx Configuration вставить содержимое
   `nginx-signal.conf` (рядом с блоком «Ogneliss Share» из `site/nginx-share.conf`) → Save.

6. **Проверить:**

   ```sh
   curl https://ogneliss.ru/share/api/v1/health
   ```

   Ответ должен быть `ok`.
   - `502 Bad Gateway` — NPM не видит службу: контейнер не запущен
     (`docker compose ps`, `docker compose logs`) или стоит в другой сети
     (`docker network inspect <сеть NPM>` должен показывать оба контейнера).
   - Ответ приходит от страницы сайта, а не `ok` — блок из `nginx-signal.conf` не
     сохранился или вставлен не в тот хост.

   Сквозная проверка комнаты (`$OWNER` — любая строка от 16 символов):

   ```sh
   API=https://ogneliss.ru/share/api/v1; OWNER=0123456789abcdefghij
   curl -X PUT -H "X-Owner: $OWNER" -d '{"ttl":60}' $API/rooms/test-room-0001   # {"expires":…}
   curl -X POST -d '{"msg":"привет"}' $API/rooms/test-room-0001/offers          # {"sid":"…"}
   curl -H "X-Owner: $OWNER" "$API/rooms/test-room-0001/offers?wait=1"          # {"offers":[…]}
   curl -X DELETE -H "X-Owner: $OWNER" $API/rooms/test-room-0001               # 204
   ```

## Обновление

```sh
git pull                        # или заново скопировать каталог server/signal/
docker compose up -d --build    # пересоберёт образ и заменит контейнер
docker image prune -f           # убрать старые слои
```

Первая сборка занимает несколько минут, дальше быстрее (зависимости кэшируются, пока не менялись
`Cargo.toml` и `Cargo.lock`). При замене контейнера все открытые комнаты теряются,
поэтому лучше обновлять, когда нет активных раздач. Журнал: `docker compose logs -f`.

## Ресурсы

- Память: в покое около 4 МиБ. Предел хранимых сообщений — 32 МиБ суммарно, так что
  контейнер укладывается в `mem_limit: 64m` даже при полной загрузке.
- Процессор: почти не нужен; ожидающие опросы — это спящие задачи, не потоки.
- Диск: ничего не пишет (файловая система контейнера `read_only`), образ — статический
  бинарник в `distroless/static`, работает от пользователя `nonroot`.
- Журнал: одна короткая строка на создание, удаление и истечение комнаты, плюс ошибки
  запуска. Содержимого сообщений в журнале нет; от имени комнаты пишутся только 6 первых символов.

## Что что ограничивает

Все тела запросов до 16 КиБ (иначе `413`); до 10 000 комнат (`503` сверх); до 64
предложений в комнате (`429`); до 120 запросов в минуту с одного IP на `PUT /rooms` и
`POST …/offers` (`429`; IP берётся из `X-Real-IP`, затем из первого адреса
`X-Forwarded-For`, их выставляет nginx из `nginx-signal.conf`, а для IPv6 считается
вся сеть /64); комната живёт до 1 часа после последнего `PUT`, срок `ttl` — 60…3600 с.
Долгий опрос ждёт до 30 секунд (по умолчанию 25).

Поэтому порт `8080` нельзя публиковать наружу: при прямом доступе клиент мог бы подделать
заголовки с адресом и обойти ограничение частоты.

## Разработка

```sh
cargo test                         # тесты работают на «замороженном» времени, сеть не нужна
cargo clippy --all-targets
LISTEN=127.0.0.1:8080 cargo run    # локальный запуск; по умолчанию слушает 0.0.0.0:8080
```

Остановка по `SIGTERM` и Ctrl-C плавная: ждущие запросы отвечают сразу, выход занимает
миллисекунды (`docker stop` не ждёт 10 секунд).
